# Node Monolith 3-Tier Application

## Overview

This is a Node.js and React-based monolithic user management web application that I used as the base for practising and implementing real-world DevSecOps engineering (from codebase modernization and containerization to full CI/CD pipelines and production-grade deployments).

> [!NOTE]
> I did not build this application from scratch. As a DevOps Engineer, my focus is on everything that happens **around the code**. This includes building, securing, packaging, and operating the application in production-like environments.
> 
> The files I added to this repository are `Dockerfile.client`, `Dockerfile.server`, `compose.yml`, `.dockerignore`, `.gitignore`, and `.env.example`. Everything else under `client/` and `server/` belongs to the original developer, with the exception of the architectural refactoring documented in Step 0.

---

## The Core Philosophy: Separation of Concerns

> Code = Input. Pipelines secure it. Infrastructure runs it.

| Repository | Role |
|---|---|
| **This repo (CI)** | Application source code and all CI/CD pipeline definitions (Jenkins, GitHub Actions) |
| **[Platform Engineering Systems (CD)](https://github.com/ibtisam-iq/platform-engineering-systems/tree/main/systems/node-monolith/3tier)** | Platform architecture (deploys, operates, and scales the artifact across multiple targets) |

> [!IMPORTANT]
> This separation is intentional. Pipeline logic lives with the code it builds, and deployment configs stay independently versioned in their own repository.

```text
├── docs/
│   ├── codebase-modernization.md   # Step 0: full audit, refactor, and migration notes
│   ├── understand-architecture.md  # Deep-dive into app structure, 2-tier vs 3-tier
│   ├── docker-setup.md             # Line-by-line Dockerfile and Compose rationale

├── Dockerfile.server               # Multi-stage build (server deps to Express runtime)
├── compose.yml                     # Local containerized environment (nginx, server, mysql)

├── .gitignore                      # Excludes .env, node_modules, client/public from version control
└── .env.example                    # Environment variable template
```

Three-tier architecture: Presentation (React SPA served by Nginx) to Business Logic (Express and MVC) to Data (MySQL).

> [!WARNING]
> **Key distinction from the 2-tier project:** Express does **not** serve static files here. Nginx is the sole entry point (port 80). It delivers the compiled React build directly and proxies all `/api/` requests to Express on port 5000. The two services run in separate containers and never share a process.

## DevOps Implementation Journey

### Step 0: Codebase Modernization

Before doing any DevOps work, I audited and modernized the inherited codebase. This involved refactoring the backend from a flat 2-tier structure into a proper MVC architecture, separating routes, controllers, models, and a connection pool into dedicated files, and modernizing all dependencies.

> [!NOTE]
> I used **AI-assisted analysis (Perplexity Pro)** for this step. Full audit notes, dependency changes, and migration details: [`docs/codebase-modernization.md`](docs/codebase-modernization.md)
> 
> As a baseline, this project is a direct evolution of **[node-monolith-2tier-app](https://github.com/ibtisam-iq/node-monolith-2tier-app)**, which is the same application prior to being refactored into a clean three-tier MVC structure with Nginx as the presentation layer.

---

### Step 1: Environment Standardization

The original codebase had hardcoded database credentials directly in `config/db.js` and `server.js`. I refactored the entire application to read all config from environment variables, making it portable across all environments.

```bash
# Copy the template and fill in real values
cp .env.example .env
```

Key variables set in `.env`:

```env
MYSQL_ROOT_PASSWORD=your_root_password
MYSQL_DATABASE=test_db
MYSQL_USER=your_username
MYSQL_PASSWORD=your_password
DB_HOST=localhost
PORT=5000
```

> [!IMPORTANT]
> For local bare-metal runs, `DB_HOST=localhost` is correct because MySQL is running directly on the same machine. When running via Docker Compose, `DB_HOST` is overridden to `mysql` (the database service name defined in `compose.yml`) via the `environment` block. Docker resolves that service name as a hostname on the internal container network, so `localhost` will not work there.

### Step 2: Local Build & Bare-Metal Validation

Before writing any Docker config, I validated the full application lifecycle locally using native MySQL, native Node.js, and Nginx. This confirmed the build was clean and the app connected to the database correctly before introducing any containerization layer.

#### 1. Install and Configure MySQL

```bash
sudo apt update && sudo apt install -y mysql-server
sudo systemctl start mysql && sudo systemctl enable mysql
sudo mysql -u root -p
```

```sql
CREATE DATABASE test_db;
CREATE USER 'your_username'@'localhost' IDENTIFIED BY 'your_password';
GRANT ALL PRIVILEGES ON test_db.* TO 'your_username'@'localhost';
FLUSH PRIVILEGES;
EXIT;
```

```bash
# Bootstrap the schema
mysql -u your_username -pyour_password test_db < database/init.sql

# Verify
mysql -u your_username -pyour_password -e "USE test_db; SHOW TABLES;"
```

#### 2. Install Dependencies and Start the Backend

```bash
cd server && npm install
node server.js
```

The server printed:

```
Server running at http://localhost:5000
Database pool connected successfully.
```

#### 3. Build the Frontend

```bash
cd ../client && npm install
npm run build
```

This created `client/public/` with `index.html`, `bundle.js`, and `style.css` (all generated by Webpack).

> [!WARNING]
> The frontend must be built **before** starting Nginx. Nginx serves the compiled static files from `client/public/`. If `public/` does not exist, Nginx will return 404 for all page requests.

#### 4. Install and Configure Nginx

Nginx acts as the reverse proxy that unifies both tiers under a single port (80). It serves static files from `client/public/` and proxies all `/api/` requests to the Express server on port 5000.

```bash
sudo apt install -y nginx

# Deploy the project's Nginx config
sudo cp nginx/default.conf /etc/nginx/conf.d/default.conf

# Remove the default Nginx site (it also listens on port 80 and takes priority)
sudo rm -f /etc/nginx/sites-enabled/default

# Grant Nginx (www-data) access to the home directory and public folder
sudo chmod o+x ~
sudo chmod -R o+r ~/node-monolith-3tier-app/client/public

# Validate config syntax and restart
sudo nginx -t && sudo systemctl restart nginx
```

> [!TIP]
> **Why `chmod o+x ~`?** Nginx runs as `www-data`. To serve files from a path inside your home directory, it must be able to traverse each directory in that path. The home directory is typically `700` (owner-only), which blocks `www-data` from entering it. `chmod o+x ~` adds traverse permission for others without exposing home directory contents.
> 
> **Why remove `sites-enabled/default`?** Nginx on Ubuntu ships with a default site that also binds to port 80. It silently takes priority over configs in `conf.d/`. Without removing it, your custom config is loaded but never used.

#### 5. Verify End to End

```bash
# Confirm the backend API is up (direct, bypasses Nginx)
curl http://localhost:5000/api/test

# Confirm the API is reachable through Nginx
curl http://localhost/api/test

# Confirm Nginx is serving the frontend
curl http://localhost
```

App runs at: `http://localhost`

> Full journey including failed approaches and fixes: [`docs/local-deployment-guide.md`](docs/local-deployment-guide.md)

### Step 3: Containerization (Docker)

With the application validated on bare metal, I wrote `Dockerfile.client`, `Dockerfile.server`, and `compose.yml` from scratch. I read `client/package.json`, `client/webpack.config.js`, `server/package.json`, `server/app.js`, and `.env.example` before writing a single line. This was to understand exactly what each image needed: build stages, output paths, exposed ports, health endpoints, and environment variable strategy.

**Key decisions I made and documented:**

- **Two separate Dockerfiles:** Because Express does not serve static files, the frontend (Nginx) and backend (Node.js) must be independent images. This is the defining difference from the 2-tier project.
- **Multi-stage `Dockerfile.client`:** Stage 1 builds the React app with Node.js and Webpack. Stage 2 copies only `client/public/` into `nginx:alpine`. The final image is lean with zero Node.js included.
- **Multi-stage `Dockerfile.server`:** Stage 1 installs production-only dependencies. Stage 2 assembles the lean runtime image.
- **`nginx/docker.conf` instead of `nginx/default.conf`:** Inside Docker, `localhost` in `proxy_pass` would point to the Nginx container itself. `docker.conf` uses the Compose service name `server` as the hostname.
- **`expose` vs `ports`:** Only the Nginx service maps a host port (`80:80`). Express uses `expose: "5000"` (reachable within the Docker network only).
- **Non-root user** in both server and client images for CIS/Trivy compliance.
- **Exec form `ENTRYPOINT`** on the server so Node.js runs as PID 1 and receives `SIGTERM` directly.
- **Healthcheck endpoints tuned per service:** Nginx uses `GET /` (port 80). Express uses `GET /api/test` (port 5000).

The full rationale for every line in all three files is in [`docs/docker-setup.md`](docs/docker-setup.md). The architectural reasoning behind why two Dockerfiles are required is in [`docs/understand-architecture.md`](docs/understand-architecture.md).

#### Validating with Docker Compose

After writing the files, I validated them end-to-end using Docker Compose by spinning up all three services (Nginx, Express, MySQL) as containers on a shared internal network.

```bash
cp .env.example .env
# Fill in: MYSQL_ROOT_PASSWORD, MYSQL_DATABASE, MYSQL_USER, MYSQL_PASSWORD, PORT

docker compose up --build
```

> [!TIP]
> `--build` forces Docker to rebuild both images from their Dockerfiles. Omit it on subsequent runs if the source code has not changed.

**What happens in sequence:**
1. Docker builds `node-monolith-3tier-app-client` (Nginx image) using `Dockerfile.client`
2. Docker builds `node-monolith-3tier-app-server` (Express image) using `Dockerfile.server`
3. The `mysql` container (MySQL 8.4 LTS) starts and runs its healthcheck (`mysqladmin ping -h localhost`)
4. The `server` container waits for the `mysql` healthcheck to pass (`condition: service_healthy`)
5. Express connects to MySQL using the service name `mysql` as the hostname
6. The `nginx` container starts and begins serving the React build and proxying `/api/` to `server:5000`
7. The app becomes available at `http://localhost`

**Verify the app is running:**

```bash
# Through Nginx (the correct production path)
curl http://localhost
curl http://localhost/api/users
```

**Stop and clean up:**

```bash
# Stop containers but keep the database volume
docker compose down

# Stop containers AND delete the database volume (full reset)
docker compose down -v
```

### Step 4: DevSecOps Pipelines (CI/CD)

The `jest.config.js` and `eslint.config.mjs` were originally absent from the codebase and generated dynamically inside the Jenkinsfile as a workaround. Recognizing this as an anti-pattern, I refactored the project to keep all configuration files directly in the codebase:

```text
server/
├── jest.config.js          # Moved out of Jenkinsfile sh block
├── eslint.config.mjs       # Moved out of Jenkinsfile sh block
├── __tests__/
│   └── health.test.js      # Basic smoke test to prevent --passWithNoTests requirement
└── package.json            # Added devDependencies and "test"/"lint" scripts

client/
├── eslint.config.mjs       # Moved out of Jenkinsfile sh block
└── package.json            # Added eslint devDependencies and "lint" script
```

With the application containerized and the configuration standardized, I moved to automating the full build-test-scan-publish cycle. I ran the Jenkins pipeline against my own self-hosted CI/CD stack (Jenkins, SonarQube, and Nexus) provisioned and documented at [nectar.ibtisam-iq.com](https://nectar.ibtisam-iq.com/operations/cicd-stack/self-hosted-jenkins-sonarqube-nexus/). The same stages were then mirrored in GitHub Actions.

**Pipeline stages (both implementations):**

| # | Stage | What it does |
|---|---|---|
| 1 | Checkout | Clone source at the correct ref |
| 2 | Trivy FS Scan | Scan source tree for secrets, misconfigs, and dependency CVEs before build |
| 3 | Versioning | Compute image tag: `<version>-<short-sha>-<build-number>` |
| 4 | Install Dependencies | Run `npm install` for both the Client and Server components |
| 5 | Build Client | Run `npm run build` to compile the React frontend |
| 6 | npm audit | Dependency scan to detect known CVEs in Node packages |
| 7 | ESLint SAST | Static Application Security Testing for JS vulnerabilities in Server and Client |
| 8 | Build & Test | Run unit tests and generate coverage reports |
| 9 | SonarQube Analysis | Static code analysis with blame info and coverage upload |
| 10 | Quality Gate | Block pipeline until SonarQube webhook fires back pass/fail |
| 11 | Docker Build | Multi-stage images (Client and Server) built once, tagged for registries |
| 12 | Trivy Image Scan | Scan both the final Client and Server Docker images for vulnerabilities |
| 13 | Push to Docker Hub | Push versioned tags and `latest` for both images to Docker Hub |
| 14 | Push to GHCR | Push both images to GitHub Container Registry |
| 15 | Push to Nexus | Push both images to self-hosted Sonatype Nexus Docker registry |
| 16 | Update CD Manifest | Commit new image tags to `platform-engineering-systems` for GitOps handoff |

The build fails hard on multiple conditions: Trivy finds CRITICAL CVEs, `npm audit` detects high-severity security flaws, SonarQube Quality Gate does not pass, or any unit test fails.

### Step 5: Platform Engineering (Deployment & Operations)

This repository strictly houses the application source code. The deployment and operational logic is intentionally decoupled into a dedicated Continuous Deployment repository to enforce a strict separation of concerns.

The Docker images generated by the CI pipeline were deployed across three increasingly advanced architectural paradigms.

**Platform Repository Structure:**

